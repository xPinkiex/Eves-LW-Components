Eve's RAM (32-bit)

Memory with a 32-bit address for the LW32 CPU block's bus: reads and writes of 1, 2 or 4 bytes, answered in one tick.

What it is

Memory with a 32-bit byte address, on the same bus as Eve's LW32 CPU: one block holds a whole program and its data, with no byte-wide RAM modules or bus logic around it. It backs the full 4 GiB address space, but only reserves memory in 512 KiB pages when something is first written there. Untouched pages read 0 and cost nothing.

Pins

Back face, lower rows: address (y = 0.5) and data in (y = 1.5) Back face, top row (y = 2.5): the bus's control Front face: data out (y = 0.5) and DATA READY (y = 1.5)

Each peg is drawn at its x position in the block's prefab, from x = 0 on the left. Small grey numbers are the peg indexes in the code. The top row of the back face is drawn on its own. RD is READ, WR WRITE, BY BYTE, WD WORD, DW DWORD, RDY DATA READY.

The control row is in the same order as the LW32 CPU block's READ, WRITE, BYTE, WORD, DWORD outputs.

The bus handshake

The LW32 CPU block's bus (lw-compiler's docs/cpu-block.md), answered as fast as it allows:

TickThe CPUThe RAM
tREAD or WRITE high, the address, the size (and the data for a write)—
t + 1waitssees it: a write is stored now; DATA READY goes high
t + 2sees DATA READY: a write is doneDATA READY low; a read's value on Q0–Q31
t + 3a read: takes the dataQ0–Q31 low again
  • Unaligned accesses work: any address, any size, wrapping at 232.
  • The data outputs are low except in a read's data tick, so they can go straight onto the shared data lines.
  • Saved with the world in the middle of an access too: the handshake's state is in the save, so after a reload the access is answered as if nothing happened (the CPU block does the same on its side).

Wiring it to the LW32 CPU

  • A0–A31 ← the CPU's address outputs. D0–D31 ← the bus's data lines (the CPU's data out). Q0–Q31 → the bus's data lines (the CPU's data in). DATA READY → the CPU's DATA READY (OR it with the devices' own).
  • BYTE, WORD, DWORD ← the CPU's size outputs, straight.
  • READ and WRITE ← the CPU's, gated by the address decoding: the RAM answers every address it sees, so it must only see its own. With the LW32 toolchain's 2g map (--target 2g: RAM below 0x80000000, the devices above, at their usual addresses with bit 31 set), that's READ AND NOT A31, WRITE AND NOT A31.
Checked outside the game: lw-compiler's emu/run-core-tests.sh runs tests/hw_tests.c built for the 2g map from this block, on the LW32 CPU block, at O0, O1 and O2, both blocks saved and reloaded every 997 ticks, and at O1 every 7 (290,000 reloads, in the middle of accesses): R1 = 0 every time. In the game since 2026-11-11: LW32 images up to 274 KB (hw_tests, cxx_probe, LW-CPU-OS) loaded with @file and ran.

Contents

  • Press X at the block for the editor, as on Eve's RAM. It loads up to 1 GiB from address 0 (@0x takes up to 8 hex digits); @file works the same, so one file holds a whole program.
  • What the world keeps: the editor's text, if there is one (a reload starts from it again), else every page that isn't all zero, and the handshake's state.
