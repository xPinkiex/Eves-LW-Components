Eve's LW32 CPU

The LW32 CPU as one block: it runs the same programs as the CPU built from gates, on the same bus, with your RAM and devices. Its core is the lw-compiler repo's emulator (native/liblw32core.so, Linux x64). In progress: not yet run in the game.

Pegs

The block is 32 wide, 3 high and 2 deep. Inputs on the back face, outputs on the front face; in each 32-bit row bit 0 is at the right (x = 31) and bit 31 at the left (x = 0), seen from the front.

IndexWhereWhat it does
in 0-31Back, bottom rowData in: the bus's data lines, read only while the CPU waits for an answer.
in 32Back, middle row, x = 0DATA READY: the device's answer (one tick). On a read the data is on the bus the tick after.
in 33Back, middle row, x = 1RUN: high to run. Looked at between instructions; an access in progress always finishes.
in 34Back, middle row, x = 2RESET: while high, the CPU is at power-on (registers, flags and PC 0) and the bus is quiet. Hold it until any answer still in flight has come.
out 0-31Front, bottom rowAddress, during an access's tick.
out 32-63Front, middle rowData out: driven only in a write's tick, low otherwise. Connect to the same bus lines as data in.
out 64-68Front, top row, x = 0-4READ, WRITE, and the size: BYTE, WORD, DWORD, for one tick per access.
out 69Front, top row, x = 5HALTED: after a Halt, or an instruction it doesn't know (the server log says which). Cleared by RESET.
Back face (inputs): data in (y = 0.5); DATA READY, RUN, RESET (y = 1.5) Front face (outputs): address (y = 0.5), data out (y = 1.5), the bus's control and HALTED (y = 2.5)

Each peg is drawn at its x position in the block's prefab, from x = 0 on the left: both faces as seen from the front (from behind, the back face is mirrored: D0 on your left), as on the 32-bit RAM's page. Small grey numbers are the peg indexes in the code. D is data in, Q data out, A the address; RDY is DATA READY, RST RESET, RD READ, WR WRITE, BY BYTE, WD WORD, DW DWORD, HLT HALTED.

The bus

  • An access: address, READ or WRITE, the size, and for a write the data, all for one tick.
  • The CPU then waits for DATA READY (one tick). On a read it takes the data the tick after; on a write DATA READY is the confirmation.
  • The next access goes out the tick after the last one finished. An instruction's own work takes one tick: its last access finishing completes it, and the next instruction's fetch goes out the tick after.
  • Accesses as the CPU's microcode makes them: the instruction as a dword read at its address, its immediate (if any) as a byte, word or dword read at address + 2, then at most one data access. So the RAM modules and devices see what they see from the hardware CPU, and the same rules apply (an access across two RAM modules fails).

With devices that answer in one to three ticks, tests/hw_tests.c (O1) takes 3.8 million ticks, against 32.9 million on the CPU built from gates.

Saving

The CPU's state (registers, flags, and where it is in an access) is kept with the world: after a reload it goes on from there, and never repeats an access. That relies on Logic World restoring the wire states with the world, so an answer in flight arrives after the reload. RAM keeps its own behaviour (Eve's RAMEve's RAM (32-bit)).

The native library

The CPU's core is built from the lw-compiler repo (emu/build-native.sh copies it here), so the block runs the same code as the emulator the compiler is tested with. It needs a 64-bit Linux server (glibc 2.16 or newer) and nothing else. At start the server log says lw32core loaded ..., or why it didn't load; without it the block does nothing. lw-compiler's emu/run-core-tests.sh runs this block's code outside the game (emu/core/blocktest, and with the 32-bit RAM emu/core/bustest).
