Eve's Network Port

A plain byte pipe between a circuit and one TCP connection: a network card for your CPU. Listen and let a terminal or a web browser connect, or connect out to any host and port.

Listen

A terminal (lwterm.py, nc) or a web browser connects to the block, one at a time.

Connect

The circuit opens a connection out, to any host and port.

One word in, one word out

Write a word: a data byte and control bits. Read a word: a received byte and status bits.

How it works

The block keeps two queues of 4,096 bytes each, one for each direction. A thread on the game server moves bytes between the queues and the socket. The pins only touch the queues, so the circuit never waits for the network. Everything is a 16-bit word, input n or output n being bit n:

  • Writing: put a word on inputs 0–15 and raise WR. The block samples all 16 on the rising edge, like the RAM's write enable: the data can arrive in the same tick as WR. Bits 0–7 are a byte; the control bits in 8–15 say what to do with it.
  • Reading: outputs 0–15 always show the status word. Bits 0–7 are the received byte, valid while READY is high.
  • Taking the byte: pulse RD_DATA, high and low again. While it's high the byte stays on the pins; when it falls, the next byte is shown, or READY goes low.
  • Acknowledging events: pulse RD_STATUS. When it falls, the sticky bits HUP and ECODE clear, so a short event between two looks is never missed.

Pins

Back face: inputs Front face: outputs

Each peg is drawn at its x position in the block's prefab, from x = 0 on the left. Small grey numbers are the peg indexes in the code; the upper row is y = 1.5, the lower y = 0.5. RDD is RD_DATA (read data), RDS is RD_STATUS (read status), HANG is HANGUP; C11–C15 are the reserved control bits; E0–E2 are the three ECODE bits.

The word written (inputs)

BitsNameWhat it does
0–7DATAA byte to send, or a command character.
8SENDSend the byte over the connection. Dropped when there is none.
9CMDThe byte is a command character (below).
10HANGUPClose the connection after what was sent before; listening goes on.
11–15—Reserved, write 0.

The strobes (inputs)

PegNameDrawn asWhat it does
16WRWRWrite. Rising edge: inputs 0–15 are sampled and the word is acted on (send, command character, hang-up).
17RD_DATARDDRead data. High, then low: the received byte on outputs 0–7 has been read. While it is high the byte stays on the pins; when it falls, the next byte is shown, or READY goes low.
18RD_STATUSRDSRead status. High, then low: the status has been read. When it falls, the sticky HUP and ECODE bits clear. Nothing else changes; the byte stays.

All three sit on the upper row of the back face, at the far left: WR, RDD, RDS.

The word read (outputs)

BitsNameMeaning
0–7DATAThe received byte, valid while READY.
8READYA received byte is in bits 0–7.
9CONNConnected. Drops in the tick HANGUP is written.
10LSNListening.
11ROOMThe send queue has room (low when 4,096 bytes wait).
12HUPSticky: the other side closed the connection, or it broke, since the last RD_STATUS. Your own HANGUP or close doesn't set it.
13–15ECODESticky: the last error since the last RD_STATUS. 0 none, 1 bad command, 2 port in use, 3 host not found, 4 connection refused, 5 timeout, 6 other.

The outputs are refreshed every tick.

Commands

Write the characters with CMD set, one word each, ending with a newline (\n) or a carriage return (\r). A new listen or connect first closes whatever was open.

CommandDoes
listen PORTWaits for connections on 127.0.0.1:PORT, only from the same machine. One at a time; others wait in line until it's closed, then the next one is accepted.
listen ADDR:PORTThe same on another address. 0.0.0.0:PORT listens on every network interface, so other machines can connect. Only do that on a trusted network.
connect HOST:PORTConnects out, to a name or address. Gives up after 10 seconds (ECODE 5).
closeCloses the connection and stops listening.
Connections aren't saved with the world. After a reload the circuit has to send its command again.

On a CPU bus

As two memory-mapped words, one address apart:

RegisterReadWrite
DATAThe status word, and its byte is taken (RD_DATA)The word: data byte and control bits
STATUSThe status word, and HUP and ECODE clear (RD_STATUS)
  • Inputs 0–15 ← data bus bits 0–15. Outputs 0–15 → data bus bits 0–15, for a read of either word.
  • WR ← write AND select (either word).
  • RD_DATA ← read AND select AND NOT A2. RD_STATUS ← read AND select AND A2.
  • Timing: hold RD high while the CPU latches the data, then drop it. If your bus writes a word as separate bytes, WR must fire once per word.

A program then:

  1. sends listen 7000 as CMD words;
  2. reads DATA in its main loop: a byte arrived when READY is set;
  3. writes SEND | byte while ROOM is set;
  4. reads STATUS now and then for HUP and ECODE.
Example: the LW32. The LW32 toolchain has this as its net device at 0x70000 (DATA) and 0x70004 (STATUS), with LW32_NET and the LW32_NET_* bits in lw32_io.h. Its emulator models the block with real sockets (lw32-emu --net). LW-CPU-OS listens on port 7000: a terminal gets a shell, a web browser gets the pages in /www.
#define DATA LW32_NET[0]
#define STAT LW32_NET[1]
static void command(const char *s) { while (*s) DATA = LW32_NET_CMD | *s++; DATA = LW32_NET_CMD | '\n'; }

command("listen 7000");
for (;;) {
    unsigned st = DATA;                         /* status, and the byte is taken */
    if (st & LW32_NET_READY) {
        while (!(STAT & LW32_NET_ROOM)) {}   /* room to send */
        DATA = LW32_NET_SEND | LW32_NET_BYTE(st);  /* echo it */
    }
}

Terminals and browsers

lwterm.py, in the mod's tools/ folder, is a small terminal for the port. It's one Python file with no dependencies, for Linux, macOS and Windows:

python3 tools/lwterm.py localhost:7000            # Ctrl+] quits
python3 tools/lwterm.py localhost:7000 --retry    # connect again after a reload
  • It puts your terminal in raw mode: every key goes out as you press it, and what comes back is printed as it arrives.
  • The circuit does the echo and line editing, like a real terminal on a serial line.
  • On connecting it sends one line, LWTERM 1. A program serving the port can tell a terminal from a web browser by the first bytes: a browser starts with GET /.... nc localhost 7000 works too, but sends nothing first and goes line by line.

A browser connects to http://localhost:7000/ like to any web server. The circuit reads the request and writes back HTTP/1.0 200 OK, headers, an empty line and the page, then sets HANGUP. Browsers open a few connections at once; the block takes them one after another.

From another machine, tunnel through SSH to the game server's machine:

ssh -L 7000:localhost:7000 you@gamepc
python3 tools/lwterm.py localhost:7000

To reach a remote shell over SSH, the PC does the encryption and the block connects to a local bridge:

socat TCP-LISTEN:7001,bind=127.0.0.1,fork EXEC:"ssh user@host",pty

Then connect 127.0.0.1:7001.

Details

  • Security: by default it listens only on 127.0.0.1, so only the game server's own machine can connect. Anyone who reaches the port talks to your circuit.
  • Latency: the server thread checks the socket every 2 ms. The circuit sees a byte on the next tick after it arrives.
  • Speed: as fast as the circuit takes the bytes.
